# Benchmarks

How NanoMatch is measured, and what the results mean. Every number here is generated by
`scripts/gen_report.py` from a raw file in [`results/`](../results), which records the commit, build flags,
machine settings and workload behind it.

## Limitations

- **This is a laptop.** Results come from a hybrid-core mobile CPU running a normal desktop Linux, without
  isolated cores or interrupt steering. An isolated server would show a different tail, particularly at
  p99.9 and above, and these numbers don't predict it.
- **Synthetic workloads.** Order flow is generated by a stated model and isn't calibrated to any real venue.
  The workload defines what the numbers mean, so results shouldn't be compared with other projects' figures
  without comparing workloads too.
- **In-process only.** Latency covers a single book processing a command in memory. Network, kernel and
  serialization costs aren't included.

## Workloads

Workloads are generated by `src/workload/generator.hpp` from a seed, using integer arithmetic only, so the same
seed gives an identical log on any toolchain. They were committed before any benchmark was run, and git history
shows the order.

The model is in the zero-intelligence style used in market microstructure research. Orders arrive at random,
placed around a reference price that wanders, and cancels pick uniformly among resting orders. A baseline book
runs inside the generator, so that crossing orders really cross and cancels name orders that are really resting.

**Command mix at steady state, in parts per 1000:**

| Profile | Passive limit | Crossing limit | Market | Cancel | Modify | Resting orders | Aggressive size |
|---|---|---|---|---|---|---|---|
| `realistic` (primary) | 480 | 30 | 10 | 380 | 100 | 10,000 | ×1 |
| `add_cancel` | 500 | 0 | 0 | 500 | 0 | 10,000 | ×1 |
| `sweep` | 600 | 150 | 50 | 150 | 50 | 10,000 | ×3 |
| `realistic_1k` | as `realistic` | | | | | 1,000 | ×1 |
| `realistic_100k` | as `realistic` | | | | | 100,000 | ×1 |
| `realistic_1m` | as `realistic` | | | | | 1,000,000 | ×1 |

- `realistic` is the primary workload: mostly adds and cancels with a small aggressive share.
- `add_cancel` never trades, and isolates book maintenance.
- `sweep` is deliberately adverse: frequent, larger aggressive orders that hit several resting orders, with enough
  passive flow to keep the book deep.
- The `realistic_*` variants show how cost scales with the number of resting orders, and with it the working
  set relative to each cache level.

**Common to every profile:**

- **Build-up:** only passive orders until the target depth is reached. After that, depth is held near the target
  by turning adds into cancels when more than 10% too deep and cancels into adds when more than 10% too shallow.
- **Reference price:** moves one tick up or down every 64 commands, so the active part of the book travels. An
  earlier draft placed orders relative to the best price, which pinned the price in place and would have flattered
  cache behaviour. That was found by inspecting the generated flow, before any benchmark ran.
- **Price placement:** passive orders go on their own side of the reference price, never crossing. 5% land up to
  2,000 ticks away. The rest land at a geometric distance, with a 25% stop probability per tick.
- **Aggressive side:** when the book's mid has lagged the reference price, 75% of aggressive orders trade towards it.
  Otherwise sides are equally likely.
- **Size:** 1 plus a geometric amount with a 15% stop probability per lot.
- **Crossing limits:** priced at the opposite best price plus a geometric reach, with a 50% stop probability.
- **Modifies:** 45% shrink the order, keeping priority where possible; 20% grow it, losing priority; the rest
  reprice it passively.
- **Stale targets:** in all profiles except `add_cancel`, 1% of cancels and modifies name an order that has
  already left the book, as when a cancel races a fill. These are rejected as `UNKNOWN_ID`.
- **Order IDs:** increase with gaps of 1 to 4.
- **Book limits:** prices 1 to 1,048,576 ticks, capacity twice the target depth.

The actual contents of each log are measured and shown below, so results don't rely on the stated mix.

## Method

**Warmup.** The first 5,000,000 commands of each log run first and aren't measured, so the book has reached
steady state.

**Measured length.** 25,000,000 commands for `realistic`, chosen to include more than 10 million new orders, and
5,000,000 for the others. Results record the exact new-order count.

**Two kinds of run, reported separately:**

- *Untimed* reads the clock only around the whole loop. This gives the true average, because per-command timers
  would inflate it, and it also collects hardware counters.
- *Timed* reads the clock around every command to give the distribution. Each value includes the timer's cost.
  That cost is measured in every run by timing nothing, and reported beside the percentiles. It isn't subtracted,
  because a single correction can't be right for every sample.

In timed runs each command is copied out of the log before the timer starts. The log is about a gigabyte in main
memory, and without this copy the samples largely measured paging through it, which a running engine reading from a
ring in cache doesn't do. An early experiment showed this clearly: all kinds of command had about the same p99.9
whatever their work, and the copy lowered it for every book. The cost of a command really crossing between threads is
measured separately, in the pipeline benchmark. Untimed runs do read the log inside the loop, for all books, so the
averages include that cost.

**Latency by kind.** Timed runs also report each kind of command separately: passive orders, aggressive orders, cancels,
modifies and rejects. The headline percentiles cover all commands together, and the breakdown is there to explain them.

**Timer.** `lfence; rdtsc; lfence`, with the TSC frequency measured against `CLOCK_MONOTONIC_RAW` in each run.

**Percentiles.** Nearest rank, from a histogram with single-tick resolution up to 4,096 ticks. Above that, 64
buckets per power of two, reporting the top of the bucket, so that rounding can only overstate latency.

**Hardware counters.** Read inside the program as one `perf_event_open` group on the P-core PMU, enabled only
around the measured loop, in user mode. `running_fraction` is recorded, because anything below 1 means the kernel
multiplexed the counters and the counts are estimates.

**Sink.** Events are written to a preallocated ring of 4,096 entries and hashed after the run. So they can't be
optimized away and their cost is included, while no I/O is measured. Every run of a book on a log must report the
same event count and hash, whatever the mode, or the harness refuses to write results.

**Machine settings.** Book runs are pinned to one P-core and use the `performance` governor, with the core's hyperthread
sibling offline. Memory mapped before the measured loop is locked. Page faults and context switches
during the loop are recorded, so a disturbed run is visible.

**Repeats.** Each configuration runs at least 3 times, with modes alternating so that slow drift such as heat
affects both. Tables show the median, and the raw files hold every run. No run is discarded. Rerunning is only for
a documented reason, and earlier files stay in `results/`.

**Ring.** One item is one push and its matching pop. Each layout runs on two separate physical cores, with a 4,096-item
ring, for an 8-byte and a 32-byte payload. Alignment of 8, 64 and 128 bytes and cached versus uncached indices show what
each design choice contributes. The intended layout also runs on hyperthread siblings and on a single core. Ping-pong
sends one item back and forth through two rings, which measures crossing time with no queue. Both the median and the
peak are reported, because a peak alone says little.

**Pipeline.** A gateway thread sends commands through the ring to a book on another core, and the event hash must match
the single-threaded result. Throughput is measured at saturation, and no latency is reported for that mode, since a full
queue would mostly measure waiting. Latency is measured by sending one command at a time, from just before the push to
just after the book finishes. The two timestamps come from different cores, which relies on this CPU's synchronized TSC.

**Timer resolution and repeatability.** One log is replayed 20 times per run, so all variation comes from the machine.
Three quantities are reported, because they differ by orders of magnitude and answer different questions: the
distribution of the timer measuring nothing, the run-to-run spread of a whole replay's average, and the spread of each
individual command's latency across replays. Every replay must also produce identical events, or the program fails.
Timing doesn't verify determinism, though. That comes from comparing event log hashes, which `make replay-check` does for
every book and threading mode, on every compiler and build type in CI.

**Turbo.** Results are reported both ways. Turbo off is steadier and is used when comparing implementations.
Turbo on is what the hardware can reach, and it varies with temperature.

**Citability.** A result file is marked citable only if it comes from a clean commit and a release build, on AC
power, with the `performance` governor and at least 3 runs. Only citable files reach the tables below.

## Reproducing

```sh
make replay-check                                         # determinism, on any machine

sudo scripts/machine_setup.sh apply --turbo off --offline 3
make bench                                                # books, repeat with --turbo on
sudo scripts/machine_setup.sh restore

sudo scripts/machine_setup.sh apply --turbo on            # needs the sibling core online
scripts/run_bench.py --suite ring
scripts/run_bench.py --suite pipeline
scripts/run_bench.py --suite jitter
sudo scripts/machine_setup.sh restore

scripts/gen_report.py
```
